# Offline app sessions

Offline access is an explicit general OIDC profile. RER registrations never accept `offline_access` or refresh tokens. It does not create an Auth browser session or carry administrator proof.

1. Register an OIDC app and its resource API through the existing Apps and Permissions doors, and assign the employee an app role.
2. Open **My account → App and device grants → Manage offline profiles** with hardware administrator proof and local email confirmed within ten minutes. Choose that app's API, the allowed API scopes, and explicit idle and absolute lifetimes in hours. Neither lifetime has an implicit default. Republishing or disabling a profile ends every older family. The API also accepts `POST /api/auth/refresh/profile` with `clientId`, `apiId`, `scopes`, `idleHours` and `absoluteHours`; `enabled:false` disables it. Scoped `apps.edit` authority uses the same existing permission and resource checks as API configuration.
3. Use the [session SDK](../packages/session-sdk/README.md) in the native host or web application. Its authorization request uses code flow, S256 PKCE, `openid offline_access`, exact API scopes, the API audience as `resource`, a device name and `dpop_jkt`. The employee sees the exact app, device, audience, API/identity scopes and both lifetimes in My account, and explicitly allows or denies each request. A role cannot consent to scopes it cannot currently exercise. Consent expires after ten minutes and produces a one-use code valid for one minute.
4. Redeem the code with the registered client authentication, PKCE verifier and an ES256 DPoP proof from the consented device key. The resource token is audience restricted and valid for at most five minutes, capped by both grant expiries. Its `cnf.jkt` binds the key. Send `Authorization: DPoP …` and a fresh DPoP proof with `ath` to the existing `POST /api/auth/resource-apis/check` door. Applications must perform this live check for each authorization decision; a cached JWT signature is not proof of current access.

Only refresh-token digests are stored. Refreshing atomically replaces the credential, advances the idle deadline without extending the absolute deadline, and retains consumed digests for reuse detection. A correctly authenticated device replaying a consumed token ends the entire family, including its resource tokens. Raw concurrent refresh requests expose reuse; there is no grace interval, cached successor or automatic retry. The SDK shares one in-flight refresh within an instance and persists its successor before publishing it. Separate instances must use the host's exclusive credential lock. Failed rotation or persistence requires a new consent; it is never hidden by sign-in or retries. Persist tokens and a nonexportable device key in the native host's secure storage or a server-held web session; do not put refresh credentials in a URL or browser local storage.

Offline grants survive ordinary browser expiry. Revoking the originating browser session, signing out everywhere, disabling or changing the person, losing the app assignment, changing employer-required upstream proof, disabling the app/profile, changing the API/profile revision, or either expiry ends current authority. My account lists each app/device with exact scopes, audience, last use, expiry and state. Employees revoke their own grants; administrators inspect scoped inventory, and revoking another person's grant retains hardware/fresh-email proof, edit scope and the existing strictly higher account rank. Reinstating a person or profile never revives an ended family.

Revocation queues the app's supported OIDC back-channel logout with the grant's `sid`; delivery uses the existing bounded retry queue. A successful local revoke does not claim that the app deleted data or that an unsupported remote session was removed. Grant, app and person endings are attributed in Activity. Scheduled maintenance also ends expired/invalid families and retries supported logout. Family authority and credentials are excluded from portable archives. Erasure uses the shared store registry and captures supported logout before removing identifiers. Retention exports only explicit credential-free family metadata and preserves source sessions while a family still references them.

The JS SDK is the current native/web application integration. AUTH-DEVELOPER-001 and AUTH-MOBILE-001 inherit the same rotation, exclusive storage, sender binding and failure semantics in future framework and native packages; AUTH-AGENT-006 retains its separate delegated-task profile. These sessions cannot call Auth administration, UserInfo or another employer/API.
