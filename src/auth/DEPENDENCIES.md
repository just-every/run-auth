Runtime packages required: `@simplewebauthn/server` 13.3.3 and `jose` 6.2.12 (now pinned by foundation in package.json/lockfile). Tests use existing wrangler's Miniflare and esbuild, plus Playwright for browser passkeys.

Wire `createAuthRuntime({db: env.DB, origin: env.AUTH_ORIGIN, secret: env.AUTH_ENCRYPTION_KEY, local: env.AUTH_LOCAL === 'true', mail: async ({to,subject,text,html}) => { ...await operatorMail(env).send(...) }})`. The runtime owns `/auth/identity/*`, `/oidc/*`, `/.well-known/openid-configuration`, `/api/auth/*`; call its `fetch(request)` before Base handlers, respecting null = unmatched. `model(request,page)` supplies real data to UI. First enrollment requires an Auth email-link session; Base sessions never confer Auth privileges. Setup remains Base-owned.

Signing secret: `AUTH_ENCRYPTION_KEY`, exactly 32 random bytes encoded base64url or 64 hex characters, Worker secret. Recovery adapter: `installRecoveryToken(db, token, now)` writes a hash only; invoke through a wrangler D1 execute adapter, never put token in committed answers. After the setup database migrations, initialize with `ensureSigningKey(runtime.context)`, which stages missing ES256 and RS256 keys without replacing existing keys. The parent setup adapter owns initialization. Per-algorithm rotation uses `stageSigningKey(context, algorithm)` or the owner-only `/api/auth/keys/stage` body `{alg: "ES256"}` / `{alg: "RS256"}`; retirement requires a mature replacement of the same algorithm. Wait JWKS_CACHE_SECONDS before activating automatically. Initial service without a published mature key returns 503 from authorization. Migration `0013_auth_token_algorithms.sql` preserves ES256 for existing clients and allows approved client records to select `id_token_signed_response_alg=RS256`. Access tokens use that same algorithm with `typ: at+jwt`, audience `<issuer>/oidc/userinfo`, a client and session binding and the granted scopes. UserInfo rechecks current authority; it offers JSON responses, no resource-API privilege and no refresh-token grant.

Linking (src/auth/links, LINKING.md) adopts Base's dependency protocol from Base main 4336124. Auth's own `/.well-known/rer-dependencies` node uses Base's `rer_dependency_installation` sector. Outbound requests to apps use `linkFetch` (default `fetch`), and tests route it to an app Worker made of Base's application side.

Base route seam: allow `/auth/bootstrap` (one-time setup owner claim), `/auth/session` (current Base session only), `/auth/signout` (local Base logout), and Base's gated `/auth/dev/enter` where existing dev wrapper owns it. Restrict all other Base `/auth/*` paths, notably `/auth/operator/status`, `/auth/operator/role`, `/auth/invite`, `/auth/operators`, `/auth/sessions`, `/auth/domain-rules` and provider mutation routes. Do not expose Base magic links/confirmation as Auth sign-in: use `/auth/identity/email/request` and `/confirm` to enforce browser binding and proof policy. After Base bootstrap, owner proves email through Auth before first passkey enrollment. Base bootstrap is never an Auth session. `/setup` still owns bootstrap state through the locked Base module. Outbox remains Base's existing key-gated `/__dev/*`.

OIDC return URL: sign-in email form must carry `returnTo` from sign-in query to email request. Confirmation returns a 303 for real form submissions and `{returnTo}` for JSON. The browser binding is HttpOnly, so the confirmation link must be opened in that browser. Signing secret accepts 64 hex characters and base64url. JWT email_verified_at is Unix seconds.

Pairwise continuity: `auth_subjects` keeps every `(client sector, person, pairwise sub)` mapping, so bindings survive a new pairwise key. Export writes a signed grant map (`auth_grant_maps`) and never carries the pairwise HMAC key or signing or wrapping secrets.

Browser proof needs devDependency `@playwright/test` and installed Chromium. Run `node --test --test-concurrency=1 tests/auth/browser.test.mjs` alongside HTTP proof `node --test --test-concurrency=1 tests/auth/security.test.mjs tests/auth/protocol.test.mjs`. Browser test uses CDP virtual hardware authenticator, native navigator.credentials and real HTTP to workerd/D1. Fake mail delivery is the only service edge.

Production key lifecycle: `/api/auth/keys/stage` and `/api/auth/keys/retire` `{kid}` require an owner passkey session. `ensureSigningKey(runtime.context)` initializes an empty store and is also called by discovery/JWKS. Publish discovery/JWKS first; newly staged keys are never used until the advertised cache lifetime elapses. Optional upstreams are configured by `upstreamProviders` in runtime options (Base IdentityProviderConfig[]); only google/microsoft/okta are accepted. `runtime.upstreamProviders()` returns the genuine enabled/visible provider links for signin UI; runtime handles their Base `/auth/oidc/<id>/start|callback` routes before the outer Base-route denial. Secret client configuration stays server-only. Google's Base verifier accepts gmail or matching hd; other presets need configured subjectEmails. Association never fabricates email proof: stale/missing local proof starts a bound-browser email reproof. Bindings cannot change person.

`rer recovery` wrapper: import `{recovery}` from `scripts/auth-recovery.mjs`; call `await recovery(argsAfterRecovery, {root})`. Supports no args or `--local` only. Invokes wrangler D1 execute auth --local --persist-to .wrangler/state, replacing unused recovery-token digests. Saves the raw token at `.rer/local/recovery-token` with mode0600 and returns `{path}`. Never print file contents. CLI direct invocation prints only the path. Real wrangler proof is tests/auth/recovery-cli.test.mjs.

Scheduled maintenance: `await maintainAuth(runtime.context)` removes expired one-time challenges/assertions/codes/rate buckets and retired key ciphertext after token expiry. It never rotates a key early; rotation is through owner-passkey APIs above. JWKS publication also removes expired retired signing material.

Dev bridge: set runtime option `allowDevSession: request => gate.admits(request)` only in the local entrypoint. Pure `amr:["dev"]` sessions are intrinsically refused without that callback and key admission. Every session containing dev is intrinsically refused when local=false. Local email/passkey sessions carry dev in protocol claims to prevent their use at production clients; their email/passkey proof remains distinct from pure dev identity. core.d.mts declares session/createSession/cookie/cookieName for the local TypeScript bridge.

Auth sessions and their cookies end at the earliest of the session lifetime, the email proof's thirty-day horizon, an attached upstream proof, and any inherited expiry. Existing sessions are also refused once their email proof lapses. Interactive authorization returns through the existing sign-in and bound email re-proof journey; `prompt=none` returns `login_required`. `prompt=login`, `max_age=0`, and an exceeded positive `max_age` require fresh authentication. The browser-bound, one-use `/oidc/authorize/resume` continuation stores the original app request and requires a new session authenticated after it began. Upstream SSO alone completes a local Auth email confirmation for a forced reauthentication request. Tokens carry the new session's `auth_time`. Pure gated dev identity retains its existing local-only session lifetime.

Discovery explicitly declares `request_parameter_supported:false` and `request_uri_parameter_supported:false`. Authorization refuses either parameter, including an empty value, with `request_not_supported` or `request_uri_not_supported` only after validating the client and its registered callback. Auth never fetches a request URI.

Required-provider domain policy: People and Sign-in methods expose `/api/auth/people/domain-rule` with `{domain, providerId}`; an empty providerId removes the rule. An Auth owner or administrator must authenticate with a passkey. Rules use the inherited `oa_domain_rules` table and match exact domains; allowed enrollment remains separately in `auth_domains`. Provider IDs must exist in private Google/Microsoft/Okta configuration. The owner is exempt. Inherited Base administrator routes remain blocked.

Changing either domain rules or allowed domains also requires Auth email confirmation within ten minutes in the requesting browser. Migration `0012_auth_local_email.sql` records this provenance on Auth sessions, independently of the shared thirty-day `auth_emails` identity proof. Existing sessions lacking this provenance continue ordinary access but must confirm locally before a domain change. The owner's provider-policy exemption never exempts local confirmation. Email step-up may preserve an active hardware session's authority and expiry; a later passkey verification may retain that browser's original email timestamp. Neither path renews an old local proof or revives a revoked source session. Session creation compares inherited authority in the D1 insert itself, so a concurrent revocation, expiry, method change or account-version change cannot restore earlier authority.

Migration `0011_auth_upstream_proofs.sql` records upstream evidence only from the verified OIDC admission adapter. Sessions and browser-bound challenges carry its opaque reference, independently of amr. Email, passkey, recovery, private-page/API session checks and authorization-code redemption recheck the current rule. A missing required provider blocks access until the owner changes or clears the rule; existing sessions and pending proofs are subject to it. Provider evidence ends within 24 hours and passkey operations cannot extend it. Provider issuer/client/subject-association changes require a new upstream sign-in; secret rotation does not.

After matching upstream sign-in, Confirm my email supplies Auth's browser-bound email proof for first passkey enrollment or recovery. Subsequent passkey authentication retains that upstream evidence. Microsoft/Okta associations with absent or stale local email proof send that additional proof directly after verified upstream admission. Upstream-only sessions never confer passkey enrollment or administrator access; actual Auth email proof is required for first enrollment, and hardware proof for administration. Trusted new upstream identities may enroll only at an exact allowed domain and through its required provider.
