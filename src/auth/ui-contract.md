# Server contract
`createAuthRuntime(options).model(request, page)` returns `{page, user, isAdmin, people, apps, methods, activity, notices}`. user: `{id,email,name,role,amr}` or null. Admin lists require passkey session; otherwise model returns only user's methods/notices. API JSON requests require same-origin `Origin` and `Content-Type: application/json`. Errors `{error}`. All mutable actions are POST.

Routes under `/api/auth`: GET `/me`, `/people`, `/apps`, `/activity`, `/methods`, `/notices`; POST `/people/domain-rule` `{domain,providerId}` (empty providerId removes the exact-domain rule), `/people/invite` `{email,name}`, `/people/domain` `{domain}`, `/people/suspend` `{personId}`, `/signout` `{}`, `/recovery/start` `{}`, `/recovery/cancel` `{recoveryId}`, `/recovery/approve` `{recoveryId}`, `/recovery/complete` `{recoveryId}`, `/recovery/token` `{token}`. Link mutations/signout-everywhere remain pending Base's app-linking APIs and must not appear as available successful actions.

Identity routes `/auth/identity/email/request` `{email}` (always 202, sets requesting-browser binding); GET `/auth/identity/email/confirm?token=...` renders confirmation form; POST same path `{token}` completes and sets Auth session, only in requesting browser. Passkeys POST `/auth/identity/passkeys/register/options` then `/register/verify` `{transaction,response}`, and `/authenticate/options` then `/authenticate/verify` `{transaction,response}`. Options replies `{options,transaction}`. Passkey authenticate reply may be `{reproof:true}`; email proof must finish in this browser. All direct browser WebAuthn calls use server options.

Every sensitive action requires Auth email confirmation on the acting session within ten minutes: passkey registration options and verification (first and additional), recovery approval and completion, `/recovery/token`, and every administration write (`/people/invite`, `/people/domain`, `/domains/add`, `/people/domain-rule`, `/people/role`, `/people/suspend`, `/keys/stage`, `/keys/retire`), which also need a hardware owner/admin session (owner for role and keys). The write itself rechecks that proof with the session's authority, so a proof that ages or a session revoked mid-request commits nothing. A registration challenge belongs to the session that requested its options; verification under any other session returns `enrollment_session_changed`, and under a revoked one nothing is stored. `localEmailConfirmed` reports that session's current proof. Missing or old proof returns `local_email_step_up_required`; Sign-in methods offers “Confirm my email”. Completion retains that browser's existing hardware authority only if its source session remains active, and retains its expiry. An independent email sign-in never gains hardware authority. A subsequent passkey verification in the confirming browser may carry its local email timestamp, without extending the ten-minute window. Upstream verification and another browser's email confirmation never supply local step-up.

`/signin` is rendered by parent via UI renderSignInPage, before Base handler. Passkey authenticate/options accepts `{returnTo}` and verify returns `{ok,returnTo}`. Preserve the transaction from options in every verify request. Owner-passkey-only POST `/api/auth/people/role` `{id,role:"admin"|"member"}` promotes/revokes administrators; owner transfer stays out of this route.

Move-in (owner/admin passkey session; writes also need the fresh local email proof): POST `/api/auth/move-in/stage` `{fileName,exportDate,text}` (up to 1 MB of file text; `201 {batchId,rows,source}`, a repeated file returns `200 {batchId,duplicate:true}`, an unreadable file `400 {error,message}`), GET `/api/auth/move-in?batch=ID` `{batches,batch,rows}`, POST `/api/auth/move-in/admit` `{batchId,rows:[idx]}`, `/api/auth/move-in/invite` `{batchId}`, `/api/auth/move-in/undo` `{batchId}`, GET `/api/auth/move-in/subjects.csv?batch=ID` (Auth0 former subjects of admitted people). The page is `/app/move-in`.
