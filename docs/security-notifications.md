# Employee security notifications

The employer's owner or administrator configures Security notification preferences in My account, using a hardware passkey and an Auth email confirmation from the last ten minutes. Saving explicitly records consent to the recipients and the report response. CT ruling RL-104 approves explicit verified channel configuration, mandatory notices and separate audited consent for Slack and destructive responses. AUTH-NOTIFY-001 remains partial for its unfinished event doors and external qualification.

New-browser notices describe the requesting app, time, approximate location where available, IP and browser. A browser recognition cookie is only a signal, never authentication. Recognition uses the last twenty successful sign-ins. Bound app sign-in requests supply their actual registered app name. Administrators can turn off new-browser and factor-enrollment notices. Once security email is authorized, recovery started, factor reset or removal, and administrator role notices cannot be disabled, including through the email channel switch.

Hardware factor enrollment, scoped help-desk factor reset, approved or emergency recovery, recovery start and direct administrator-role grants call the notice engine only after their source writes succeed. Mail goes to the affected person's current verified address. Successful explicit scoped administrator grants also record a required notice in the same guarded transaction as the grant and its operation. Existing positive role ranks define administrator grants, including custom roles; ordinary zero-rank roles retain their classification. Preview, refused, stale and replayed applications create no intent. Every new notice carries a signed report action valid for seven days; it contains no sign-in credential. Recovery-started notices also name the existing signed-in cancellation path. The earlier recovery mail and session notices remain in place.

The scoped-grant intent binds the committed operation, grant and verified work address. Before channel setup, it remains actionable in Follow-up rather than disappearing. After setup, scheduled maintenance resumes unattempted intents. If the person is erased, inactive or no longer has that verified address, delivery refuses instead of choosing a new recipient. A single persisted attempt records accepted, failed or unknown delivery; failed or interrupted attempts remain unresolved in Follow-up and are never automatically resent. These obligations authorize no additional reminders. They are installation-local and excluded from portable archives, so restore cannot replay an old mail attempt. Transport acceptance is not a receipt of delivery.

Opening Report suspicious activity works while signed out and consumes the signed action once. Forgery, expiry, reuse and a different employer all refuse. The report records its originating notice and event, appears in Activity and the lifecycle event stream, and opens a security-owner follow-up. An administrator can mark that investigation reviewed; sending a message never closes it.

The optional end-sessions response revokes Auth sessions and refresh grants in the report transaction, then sends the existing linked-app identity fence and native app back-channel logout. The optional Slack escalation posts once to the configured incoming webhook, recording accepted, failed or unknown outcomes without silently retrying an uncertain post. The installation's webhook is not inherited by another employer.

Operators configure `AUTH_NOTIFICATION_SLACK_WEBHOOK` as a server-only secret. Existing mail settings remain `MAIL_PROVIDER`, `MAIL_FROM` and `MAIL_API_KEY`; SendGrid is supported by the existing mail module. Do not put the webhook or mail credentials in client settings, a repository or logs.

Remaining obligations stay with AUTH-NOTIFY-001: push through AUTH-AUTHENTICATOR-001; password changes and lockout through AUTH-PASSWORD-001; temporary access pass notices through AUTH-TAP-001; every role-grant path outside the existing explicit scoped grant action and remaining factor-removal doors; connected SaaS session revocation through AUTH-LOGOUT-002; additional response policies and configured SIEM qualification. Required-notice intent coverage before setup at other event doors remains open under RL-104. This slice does not claim those outcomes.
